# Online Selling & Inventory Management System (Web + Telegram)

Architecture: **Modular Monolith** applying Domain-Driven Design, .NET 10 + PostgreSQL (backend), React + Vite + TypeScript (frontend).

## Directory structure

```
backend/
  OnlineShop.sln
  Directory.Build.props        # TargetFramework net10.0, Nullable enable shared by every project
  src/
    BuildingBlocks/            # Entity, AggregateRoot, ValueObject, IDomainEvent, Result<T>, Guard, IUnitOfWork
    Modules/
      Identity/{Domain,Application,Infrastructure}
      Catalog/{Domain,Application,Infrastructure}
      Inventory/{Domain,Application,Infrastructure}
      Ordering/{Domain,Application,Infrastructure}
      AiAdvisory/{Domain,Application,Infrastructure}
      Notification/{Domain,Application,Infrastructure}
    Api/                        # ASP.NET Core host (Presentation layer) — references every module's Application + Infrastructure
  tests/                        # (test projects to be added per module in later phases)
web/                            # React + Vite + TypeScript (Buyer storefront & Seller dashboard)
docker-compose.yml              # PostgreSQL for local dev
```

Module boundary rule (per the Context Map in the plan): a module may only call another module through that module's **Application layer** (never reach directly into another module's Domain/Infrastructure). Domain Events between modules are handled in-process via MediatR within the same transaction.

### Post-launch additions

- **Category Update/Delete, Product Delete**: Catalog previously only supported Create (+Update for Product). Deleting a Category is blocked with a clear error if it still has products; deleting a Product raises a domain event so Inventory cleans up the now-orphaned stock record. Admin UI: inline edit + delete on the Categories page, delete on the Products list.
- **Known, accepted gap**: no "forgot password" flow — reasonable to skip at this project's scope, flagged here rather than silently missing.
- Catalog now has 85 products across 6 categories (14–15 per category) — enough that filtering by any single category on the homepage (`pageSize=12`) always spans at least 2 pages, so pagination is actually exercised during a normal demo instead of only in a synthetic test. Added via the real Admin API (create + receive-stock) exactly like the earlier catalog-diversification round, not raw SQL.
- **Shipping address on Order**: checkout (Web and Telegram) now collects a required delivery address (recipient name, phone, address line, city) as a `ShippingAddress` value object frozen onto the `Order` at placement time — mirrors `Money`'s snapshot pattern, so a later change to where the buyer lives never rewrites an already-placed order. Shown on both the buyer's order detail page and the Seller/Admin order detail page (the seller needs it to actually ship). On Telegram, choosing a payment method now prompts for one reply message with the 4 fields comma-separated before the order is placed. Pre-existing demo orders were backfilled with a placeholder address via the migration's column defaults.
- **Product reviews & ratings**: any Buyer can leave one 1–5 star rating + optional comment per product (`ProductReview`, its own Aggregate Root in Catalog — not a child of Product, so browsing/editing products never has to load every review). Average rating and review count are computed with a same-schema SQL aggregate and shown on both product cards and the product detail page, which also lists every review and lets a Buyer submit their own. **Known, accepted simplification**: reviews aren't gated to "verified purchase" — enforcing that would require the Catalog module to read Ordering's data, which the existing dependency direction (Ordering.Application → Catalog.Application) blocks without an Api-layer composition step; skipped as out of scope for this project's size, but worth mentioning if the mentor asks.
- **Multiple images per product (gallery)**: Product keeps its existing single `ImageUrl` as the cover photo, and now also owns a `ProductImage` child collection (its own Aggregate boundary, not a separate one — a gallery has no lifecycle of its own) for extra photos, managed from the admin product form (upload/remove) and shown as a click-to-switch thumbnail strip on the product detail page. Fixed two real bugs found while building this: (1) `LocalFileStorageService` named every upload `{productId}.ext`, so a second image for the same product silently overwrote the first — renamed to `{productId}_{newGuid}.ext`; (2) adding a new child entity to an already-persisted aggregate's collection (loaded via `Include`) hit the same "EF Core treats a client-generated Guid key as pre-existing and issues a no-op UPDATE instead of an INSERT" gotcha already documented on `InventoryTransactionConfiguration` — fixed the same way (`ValueGeneratedNever()` on the id property).
- **Wishlist / Favorites**: a `Wishlist` Aggregate in Ordering (same shape as `Cart` — one per Buyer, server-side so it's shared between Web and Telegram) lets a Buyer heart a product from the product grid or its detail page. `WishlistContext` mirrors `CartContext` and drives a heart icon (♡/♥) everywhere a product appears, plus a `/wishlist` page to review and either add-to-cart or remove each item.
- **Related products & Recently viewed**: the product detail page shows up to 4 other products from the same category (reuses the existing `GET /products?categoryId=` search, no new endpoint) and a "Recently viewed" row driven by a small `localStorage` list (client-side only — this is a UX nicety, not state that needs to sync across devices/channels the way Cart/Wishlist must, so no server round-trip). The homepage shows the same "Recently viewed" row when no search/category filter is active.
- **Voucher / discount codes at checkout**: a new `Voucher` Aggregate in Ordering (Percentage or FixedAmount, optional max-uses and expiry) that Admin/Seller manage from `/admin/vouchers`. At checkout, a Buyer can preview a code (`GET /vouchers/preview`, no side effect) before confirming; on `Checkout`, the voucher's discount is computed and frozen onto the Order (`Subtotal`, `DiscountAmount`, `VoucherCode`, `TotalAmount = Subtotal − DiscountAmount`, clamped at zero) and the voucher's use count is incremented in the same transaction — consistent with this codebase's existing precedent of `CheckoutCommandHandler` already touching two aggregates (Cart + Order) in one `SaveChanges`. Both the buyer's and the Seller/Admin's order detail pages show the subtotal/discount/total breakdown.
- **Visual order status timeline**: both order detail pages (buyer and Seller/Admin) now show a step tracker (Pending → Approved → Shipping → Completed) alongside the existing status badge, with a red branch step for Cancelled/Returned instead of forcing those onto the happy path.
- **Breadcrumb navigation**: added to the product detail page (Home / Category / Product) and every buyer account page (Cart, Wishlist, Checkout, My orders, Order detail) — frontend-only, no new endpoints.
- **"Sold" badge on product cards**: shows `N sold` next to stock, computed by reusing the existing `GetProductSalesStatsQuery` (built in Phase 8 for the AI restock report) and merging it into Catalog's product DTOs **at the Api controller**, not inside Catalog itself — Catalog can never depend on Ordering.Application (the reverse dependency already exists), so this is the one architecturally-correct place to combine "how many units sold" with product data. Only counts confirmed orders (Approved/Shipping/Completed), matching the existing sales-stats definition.

- **Select individual items at checkout**: previously, "Proceed to checkout" always checked out the *entire* cart — a buyer who wanted to hold off on one item had no way to do that without removing it first (losing it from the cart entirely). Added per-line checkboxes + a "select all" toggle to `CartPage.tsx` (everything defaults to selected, matching the old behavior for anyone who never touches a checkbox); the selected product ids travel to `/checkout` via router state. Backend: `CheckoutCommand`/`CheckoutRequest` gained an optional `ProductIds` list — null/empty still means "the whole cart," so the Telegram bot (which has no item-picker UI) keeps working completely unchanged with zero bot-side code touched. `CheckoutCommandHandler` filters `cart.Items` to the selection before building order lines, and after a successful order removes *only* the checked-out items (looping the existing `Cart.RemoveItem`) instead of calling `Cart.Clear()`, so unselected items survive in the cart. `PreviewVoucherQuery`/`PreviewVoucherQueryHandler` got the same optional `ProductIds` filter so a previewed discount is computed against the same subtotal that will actually be charged (a percentage voucher previewed against the full cart would otherwise show a bigger discount than what checkout actually applies to a partial selection) — `CheckoutPage.tsx` passes its selection into both the preview call and the final checkout call. One frontend implementation detour worth noting: the first `CartPage.tsx` version tracked selection with `useState` + a `useEffect`/`useRef` reconciliation (to auto-select newly-added items while preserving explicit deselections); it worked in production builds but silently ended up with an empty selection under React 19 + `StrictMode`'s dev-only double-invocation of state-updater functions, because the updater mutated an external ref as a side effect — precisely what that diagnostic exists to catch. Replaced with a purely derived value (`selected = cart.items not in an explicit "deselected" Set`), which needs no effect at all and is immune to double-invocation by construction. Verified live end-to-end (curl): checking out one of two cart items leaves the other one in the cart with its own quantity intact, the resulting order contains only the selected line, a follow-up full-cart checkout (no `productIds`, simulating the Telegram bot) still clears everything, and a 10%-off voucher previews as 15,000₫ off a 150,000₫ single-item selection vs. 111,000₫ off the same voucher against the full 1,110,000₫ cart. Also verified via a temporary Playwright pass driving the real checkboxes, select-all, the checkout page's filtered item list/subtotal, and the post-order cart state. Full 93-test backend suite unaffected (pure additive parameter, defaults preserve every existing call site).
- **Price range & rating filters**: the search endpoint already accepted `minPrice`/`maxPrice` since Phase 2, but the storefront never exposed any UI for them. Added min/max price inputs and a "★ & up" rating dropdown to the homepage's filter bar, plus a new `minRating` parameter threaded through `GetProductsQuery`/`ProductSearchFilter` down to `ProductCatalogQueries` (filters on the same average-rating subquery already used for the review-count badge, so no extra query cost). A "Clear filters" button appears whenever any of these are active.

- **Hardening follow-ups**: (1) `AddProductGalleryImageCommand` was missing the same file-extension validator the primary image-upload endpoint already had — fixed (`AddProductGalleryImageCommandValidator`, same jpg/jpeg/png/webp allowlist). (2) The Api now runs every module's pending EF Core migrations on startup (`Program.cs`, before the Identity seeder) — without this, a fresh Postgres volume (e.g. a first `docker compose up` on another machine) had no schema at all and every request 500'd. (3) `/api/auth/login` is now rate-limited (10/min per IP, same fixed-window approach as the AI endpoints) against brute-force guessing. (4) Added a `GET /health` liveness endpoint. (5) Added 37 new unit tests (`VoucherTests`, `WishlistTests`, `ShippingAddressTests`, `ProductReviewTests`, `OrderingMoneyTests`, plus 3 new `OrderTests` cases) covering this session's new aggregates and the discount-clamping logic on `Order` — 77 unit tests total, 87 with integration tests.

### Other fixes made along the way
- `LocalFileStorageService` (image uploads) named every file `{productId}.ext`, so uploading a second image for the same product silently overwrote the first — fixed to `{productId}_{newGuid}.ext` (surfaced by the new product-gallery feature, but affected the original single-image upload too).
- **Real bug surfaced by adding auto-migration**: `CustomWebApplicationFactory` (integration tests) pre-migrated each module's `DbContext` standalone before booting the test host, but built its `DbContextOptions` without the schema-qualified `MigrationsHistoryTable(...)` call every module's real DI registration uses — so its pre-migration recorded history in the default `public.__EFMigrationsHistory` table while the real app checks e.g. `identity.__ef_migrations_history`. Nothing had ever re-run migrations against an already-migrated test DB before, so this silently did nothing wrong — until the new startup auto-migration did exactly that and hit `relation "roles" already exists`. Fixed by making the factory's `BuildOptions` configure the same schema-qualified history table as production.
- **Header redesign**: Cart and Wishlist moved out of the left nav and into icon buttons (🛒/♡, with the same unread-style count badge) on the right, next to a new circular avatar (first letter of the buyer/staff's name) that replaces the old "Fullname · Role" text pill. Hovering the avatar shows a dropdown with the full name, username, role, a "View profile" link, and "Log out" (removed from its old always-visible spot); clicking the avatar itself navigates to `/profile`. `ProfilePage.tsx` is now a proper account dashboard: a header card (avatar + name/username/role + a Buyer-only stats row linking to Orders/Wishlist/Cart), a labeled account-details card, a role-based quick-links card, and the existing change-password form. Verified live via Playwright for both a Buyer and Admin login (icons only show for Buyer; hover panel shows the right name/username/role; clicking the avatar reaches the enhanced profile page; badges update after adding to cart/wishlist).
- **Seventh hardening round**: fixed a real Telegram-formatting bug — every bot text response is sent with `parseMode: Markdown`, but `BotText.ProductDetail`/`BotText.Cart` interpolated a product's Name/Description (Admin/Seller-authored, not sanitized for Markdown) straight into the message with no escaping. Any of Telegram's legacy-Markdown special characters (`_ * ` [`) in a product name or description — plausible by accident, e.g. "iPhone_128GB" or a description with a `*bolded*` note — would either mangle the message's formatting or make Telegram's API reject the send outright ("can't parse entities"), breaking that product's page in the bot for every buyer. Added a small `Escape()` helper in `BotText.cs` and applied it to every interpolated dynamic string in the two affected methods (`ProductLine`/`OrderLine`/`LinkSuccess` don't need it — verified each is either plain-text-only or never actually sent with Markdown parse mode). Verified by actually invoking the real compiled `BotText.ProductDetail`/`Cart` methods via a throwaway reflection harness with a deliberately-malicious product name (`iPhone_14 *Pro* Max\`128GB\`[NEW]`) — confirmed the real output correctly backslash-escapes every character, leaving only the bot's own intentional bold markers as real Markdown — rather than trusting a hand-traced guess, and without sending an actual live Telegram message to a real chat. Full 93-test suite unaffected (pure string-formatting change).
- **Sixth hardening round — stock-availability warnings at cart/checkout time**: previously, adding to cart, updating a cart quantity, or checking out never checked the requested quantity against available stock at all — a buyer could add 999 units of a product with 5 in stock and only discover it was impossible when Seller/Admin later rejected the order at Approve time (the point where stock has always been authoritatively enforced, per the Phase 4 design — that enforcement is unchanged). Added a soft, buyer-facing check in `AddCartItemCommandHandler` (rejects if the new total for that product would exceed `StockQuantity`, with a message noting how many are already in the cart), `UpdateCartItemQuantityCommandHandler` (same check, skipped when lowering quantity or removing the line), and `CheckoutCommandHandler` (re-checks at the moment of order placement, since stock can move between add-to-cart and checkout). All three surface a clean `Product.InsufficientStock` 400 that the existing frontend error-alert plumbing already displays with no UI code changes needed. Verified live end-to-end: adding beyond stock, raising quantity beyond stock, and checking out exactly at the stock ceiling all behave correctly; confirmed the error renders in the actual product-detail page via Playwright, not just via curl. Fixed one real regression this surfaced in `OrdersApiTests.GetOrderById_AsDifferentBuyer_ReturnsForbidden`'s test fixture, which created a product and immediately tried to check it out without ever giving it any stock — added a stock-receive step matching how a real product is actually set up. Full 93-test suite still green.
- **Fifth hardening round**: fixed a real bug in the Telegram checkout flow — the bot asked for shipping details as exactly 4 comma-separated values (`Full name, Phone number, Address, City`), but a real street address very often has its own internal comma (e.g. "12 Nguyen Trai, Thanh Xuan"), which made the parser see 5 parts and reject every such reply outright — nobody could actually check out via Telegram with a realistic address. Fixed in `TelegramUpdateDispatcher.HandleShippingAddressReplyAsync`: the first value is always the name, the second the phone, the *last* is always the city, and everything in between (however many commas that spans) is rejoined into one Address string — verified correct by tracing both the plain 4-part case and a 5-part case with an embedded comma by hand against the exact `Split`/range-slice logic used.
- **Fourth hardening round**: fixed a real "expires on" date bug in the voucher admin UI — a plain `new Date("2026-09-15")` from a `<input type="date">` parses as midnight *UTC*, so a voucher set to "expire on" a given day was actually already expired from the very start of that day, not usable through the end of it as an admin would expect. Fixed by anchoring to 23:59:59.999 *local* time before converting to UTC (`dateInputToEndOfDayIso` in `AdminVouchersPage.tsx`), and fixed the reverse direction too (`toDateInputValue` now reads the browser's local calendar date off the stored UTC timestamp instead of naively slicing the ISO string, which could show the wrong day back when re-opening a voucher for edit depending on timezone). Verified live: created a voucher expiring "today," confirmed it's still valid and usable at checkout right now (not already expired); confirmed editing that same voucher shows the same date back with no off-by-one-day drift.
- **Third hardening round**: fixed a real voucher-lifecycle bug — cancelling or returning an order that used a limited voucher (`MaxUses`) permanently burned that use even though the discount was never actually redeemed; `Voucher.ReleaseUse()` now decrements `UsedCount` when `CancelOrderCommandHandler`/`ReturnOrderCommandHandler` process an order that has a `VoucherCode`. Vouchers can now be **edited** (`PUT /api/vouchers/{id}` — discount type/value, max uses, expiry; the code itself stays immutable) instead of only Create+Deactivate, matching the earlier Category/Product CRUD fix; editing a voucher's `MaxUses` below its already-used count is rejected. Fixed a real resource leak: deleting a product, removing a gallery image, or replacing the cover photo never deleted the actual file from `wwwroot/uploads` — only the DB row — so orphaned images accumulated on disk forever; added `IFileStorageService.DeleteAsync` (best-effort, missing file is not an error) and wired it into `DeleteProductCommandHandler` (deletes the cover photo + every gallery image), `RemoveProductGalleryImageCommandHandler`, and `UploadProductImageCommandHandler` (deletes the previous cover photo when replaced). All verified live (curl): a `MaxUses=1` voucher used then cancelled correctly goes back to `usedCount: 0` and previews as valid again; editing a voucher's discount type/value/expiry sticks; the uploads folder's file count returns to baseline after deleting a product with a cover + gallery image. 6 new unit tests added for `Voucher.ReleaseUse`/`UpdateDetails` (93 tests total).
- **Second hardening round**: CORS is now configured (`Cors:AllowedOrigins` in appsettings, defaults to the dev origins; falls back to allow-any if left empty) — the JWT travels in the `Authorization` header, never a cookie, so no `AllowCredentials()` was needed. Fixed the long-known Vietnamese-diacritics search gap: enabled Postgres's `unaccent` extension via a new migration, mapped it into EF Core as a `DbFunction` on `CatalogDbContext` (schema-qualified to `public`, since the extension installs there while the module's own tables live under `catalog`), and now compare `unaccent(name) ILIKE unaccent(keyword)` instead of a plain `ILIKE` — a search for "áo" now matches a name stored as "Ao" and vice versa (two real EF-translation issues surfaced getting this right: `string.Format`-based interpolation broke once one operand was a mapped function call — switched to plain `+` concatenation — and the function needed an explicit `HasSchema("public")` or EF prefixed it with the DbContext's own default schema). Image uploads (both the cover photo and gallery images) are now also checked by real file content — a shared `ImageContentValidator.LooksLikeAnAllowedImage` peeks the first bytes for the JPEG/PNG/WEBP magic numbers, so renaming a non-image file to `.png` no longer gets past the extension-only check. Buyers/Sellers/Admins can now change their own password (`POST /api/auth/change-password`, verifies the current password first) from a new `/profile` page (linked from the header's user chip). Seller/Admin can now delete any product review (`DELETE /api/products/{id}/reviews/{reviewId}`) for moderation — a Buyer still cannot delete their own. `web/README.md` was rewritten with real project content (was still the default Vite template). All verified live (curl + a temporary Playwright pass) and via the full 87-test suite.
